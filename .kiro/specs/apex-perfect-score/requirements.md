# Requirements Document

## Introduction

The APEX Perfect Score feature closes the four remaining gaps that prevent the APEX Movie Recommendation System from achieving a 10/10 rating across all evaluation dimensions. The system currently scores 9.5/10 on ML Completeness (ensemble weights for KAN, Hyperbolic, and Diffusion are zero; offline evaluation metrics are pending), 8.5/10 on Testing Completeness (five property tests from the adaptive-serving-tiers spec are unwritten; no coverage gate; no mutation testing), 6.5/10 on Frontend Completeness (the React SPA exposes only a fraction of the backend's capability), and 8/10 on Spec Completeness (four tasks from the adaptive-serving-tiers spec remain partially implemented).

These four gaps are addressed as a single cohesive feature set so that every dimension reaches 10/10 simultaneously. The work is organized into four requirements groups that can be executed in parallel where dependencies allow.

## Glossary

- **Ensemble_Engine**: The `ApexEnsembleEngine` class in `backend/ensemble_engine.py` that fuses scores from all six models (LightGCN, Quantum, SASRec, KAN, Hyperbolic, Diffusion).
- **Weight_Optimizer**: The offline Dirichlet grid-search script at `scripts/optimize_ensemble_weights.py` that evaluates candidate weight vectors and persists the best to `models/ensemble_weights.json`.
- **Offline_Eval_Pipeline**: The leave-one-out evaluation pipeline that computes NDCG@10, Recall@50, ILD, and Cold-Start NDCG@10 against MovieLens 100K and writes results to `reports/offline_eval_report.json`.
- **Offline_Eval_Endpoint**: The new `/v1/evaluation/offline-metrics` API endpoint that serves the contents of `reports/offline_eval_report.json`.
- **NDCG**: Normalised Discounted Cumulative Gain — the primary offline ranking metric.
- **ILD**: Intra-List Diversity — mean pairwise cosine distance between SBERT embeddings of the top-10 recommended items.
- **Cold_Start_User**: A user with five or fewer training interactions in the leave-one-out split.
- **Coverage_Gate**: The minimum line-coverage threshold (80%) enforced in `ci.yml` that fails the build when coverage drops below the threshold.
- **Mutation_Testing**: The practice of introducing small code mutations and verifying that the test suite detects them, using `mutmut` or `cosmic-ray`.
- **HardwareProfile**: The dataclass in `backend/serving_tier.py` containing `gpu_available` (bool), `ram_gb` (float), and `cpu_cores` (int).
- **TierDetector**: The startup component in `backend/serving_tier.py` that resolves the active serving tier.
- **ONNXEngine**: The `ONNXEngine` class in `backend/onnx_engine.py` that runs ONNX Runtime inference sessions.
- **Recommender**: The main orchestration class in `backend/recommender.py` that coordinates the 10-stage recommendation pipeline.
- **Serving_Tier**: One of three named capability levels — `tier1`, `tier2`, or `tier3`.
- **React_SPA**: The React 19 + TypeScript + Vite 7 single-page application in the `frontend/` directory.
- **SLO_Endpoint**: The existing `/v1/platform/slo` API endpoint that returns live SLO metrics.
- **KG_Endpoint**: The existing `/v1/recommendations/knowledge-graph/{movie_id}` API endpoint.
- **Evaluation_Endpoint**: The existing `/v1/evaluation/semantic-benchmark` and `/v1/evaluation/recommendation-benchmark` API endpoints.
- **User_Features_Endpoint**: The existing `/v1/events/features` API endpoint that returns behavior features for a user.
- **Admin_Dashboard**: The existing `admin_dashboard.html` static page that exposes the reload-ensemble-weights button and system controls.
- **Vitest**: The test runner used by the React frontend (`vitest`).
- **axe_core**: The accessibility audit library (`@axe-core/react` or `axe-core`) used to detect WCAG violations in the frontend CI job.
- **Retrieval_Provenance**: The `retrieval_stage` and `retrieval_signals` fields on each recommendation result that identify which pipeline stage produced the result.
- **LLM_Explanation**: The `explanation_text` field on each recommendation result containing a natural-language explanation generated by GPT-4o or Llama 3.
- **Knowledge_Graph_Path**: The multi-hop graph path (director → genre → franchise → actor edges) that explains why a movie was recommended via the KG stage.
- **D3_Force_Graph**: A force-directed graph visualization built with D3.js or Cytoscape.js that renders Knowledge_Graph_Path data.

## Requirements

### Requirement 1: Run Ensemble Weight Optimizer Against Real Interaction Data

**User Story:** As a recommendation engineer, I want the ensemble weight optimizer to be executed against real MovieLens interaction data so that KAN, Hyperbolic, and Diffusion models receive non-zero weights that reflect their actual contribution to ranking quality.

#### Acceptance Criteria

1. WHEN `scripts/optimize_ensemble_weights.py` is executed with at least 500 Dirichlet candidates, THE Weight_Optimizer SHALL evaluate each candidate against the validation split of the Event Store and compute NDCG@10 and Hit_Rate@10.
2. WHEN the Weight_Optimizer completes, THE Weight_Optimizer SHALL persist the best-performing weight vector to `models/ensemble_weights.json` with all six keys (`lightgcn`, `quantum`, `sasrec`, `kan`, `hyperbolic`, `diffusion`) having non-negative values that sum to 1.0, and at least one weight SHALL be greater than 0.001.
3. WHEN `models/ensemble_weights.json` is written by the Weight_Optimizer, THE Weight_Optimizer SHALL include metadata fields `evaluated_at`, `ndcg_at_10`, `hit_rate_at_10`, and `num_candidates_evaluated` alongside the weight values.
4. WHEN the Weight_Optimizer produces a best weight vector, THE Weight_Optimizer SHALL log the top-5 candidate vectors and their NDCG@10 scores to stdout before writing the output file.
5. WHEN the Ensemble_Engine loads at startup and `models/ensemble_weights.json` exists with non-zero values for `kan`, `hyperbolic`, or `diffusion`, THE Ensemble_Engine SHALL use those values instead of the hard-coded defaults (`kan=0.00`, `hyperbolic=0.00`, `diffusion=0.00`).

### Requirement 2: Complete Offline Evaluation Pipeline

**User Story:** As a recommendation engineer, I want a complete offline evaluation pipeline that computes NDCG@10, Recall@50, ILD, and Cold-Start NDCG@10 on a leave-one-out split of MovieLens 100K, so that the whitepaper's Section 6.1 can be populated with actual numbers.

#### Acceptance Criteria

1. THE Offline_Eval_Pipeline SHALL implement a leave-one-out split: for each user in MovieLens 100K, the most recent interaction is held out as the test item and the remaining interactions form the training set.
2. WHEN the Offline_Eval_Pipeline runs, THE Offline_Eval_Pipeline SHALL evaluate all 9,724 rated movies as the candidate pool for each user (full catalog evaluation).
3. THE Offline_Eval_Pipeline SHALL compute NDCG@10 over the held-out test items across all users.
4. THE Offline_Eval_Pipeline SHALL compute Recall@50 over the held-out test items across all users.
5. THE Offline_Eval_Pipeline SHALL compute ILD as the mean pairwise cosine distance between SBERT embeddings of the top-10 recommended items for each user, then averaged across all users.
6. THE Offline_Eval_Pipeline SHALL compute Cold-Start NDCG@10 on the subset of users with five or fewer training interactions.
7. WHEN the Offline_Eval_Pipeline completes, THE Offline_Eval_Pipeline SHALL write results to `reports/offline_eval_report.json` with fields `ndcg_at_10`, `recall_at_50`, `ild`, `cold_start_ndcg_at_10`, `evaluated_at`, `num_users`, `num_cold_start_users`, and `candidate_pool_size`.
8. WHEN a GET request is made to `/v1/evaluation/offline-metrics`, THE Offline_Eval_Endpoint SHALL return the contents of `reports/offline_eval_report.json` as a JSON response.
9. IF `reports/offline_eval_report.json` does not exist when `/v1/evaluation/offline-metrics` is called, THEN THE Offline_Eval_Endpoint SHALL return a 404 response with a message indicating the evaluation has not been run yet.
10. WHEN the Offline_Eval_Pipeline completes, THE Offline_Eval_Pipeline SHALL update `docs/APEX_WHITEPAPER.md` Section 6.1 by replacing the "Pending offline eval run" placeholders with the computed metric values.

### Requirement 3: Add Code Coverage Enforcement Gate

**User Story:** As a platform engineer, I want the CI pipeline to fail when line coverage drops below 80%, so that the test suite quality is enforced automatically on every pull request.

#### Acceptance Criteria

1. WHEN the `unit-tests` job in `ci.yml` runs, THE Coverage_Gate SHALL measure line coverage for the `backend` package using `pytest-cov`.
2. WHEN measured line coverage is below 80%, THE Coverage_Gate SHALL fail the `unit-tests` CI job with a non-zero exit code; WHEN measured line coverage is exactly 80%, THE Coverage_Gate SHALL allow the job to pass.
3. WHEN measured line coverage is 80% or above, THE Coverage_Gate SHALL allow the `unit-tests` CI job to pass.
4. THE Coverage_Gate SHALL produce a coverage XML report (`coverage.xml`) and upload it as a CI artifact regardless of whether the gate passes or fails; IF coverage measurement itself fails, THE Coverage_Gate SHALL produce an empty or error report rather than omitting the artifact entirely.
5. WHEN the `frontend-tests` job in `ci.yml` runs, THE Coverage_Gate SHALL measure line coverage for the React frontend using Vitest's `--coverage` flag.
6. WHEN measured frontend line coverage is below 80%, THE Coverage_Gate SHALL fail the `frontend-tests` CI job.
7. THE `README.md` SHALL include a coverage badge that links to the most recent coverage report.

### Requirement 4: Write Missing Property Tests from Adaptive-Serving-Tiers Spec

**User Story:** As a platform engineer, I want the five property tests specified in the adaptive-serving-tiers spec to be implemented, so that the hardware detection, tier resolution, ONNX thread binding, and orjson round-trip behaviors are verified by automated property-based tests.

#### Acceptance Criteria

1. THE system SHALL implement Property 1 (`HardwareProfile` type invariants): for any combination of mocked `torch.cuda.is_available`, `psutil.virtual_memory`, and `os.cpu_count` return values (including error-raising callables), `TierDetector.detect()` SHALL always produce a `HardwareProfile` where `gpu_available` is `bool`, `ram_gb` is `float > 0`, and `cpu_cores` is `int >= 1`.
2. THE system SHALL implement Property 2 (tier resolution totality): for any `HardwareProfile` instance with arbitrary `ram_gb` and `gpu_available` values, `TierDetector.resolve()` SHALL always return a value in `{"tier1", "tier2", "tier3"}` and SHALL never raise an exception.
3. THE system SHALL implement Property 3 (auto-selection boundary conditions): for any `HardwareProfile` where `ram_gb < 8.0`, `TierDetector._auto_select()` SHALL return `"tier3"`; where `gpu_available == True` and `ram_gb >= 16.0`, it SHALL return `"tier1"`; otherwise it SHALL return `"tier2"`.
4. THE system SHALL implement Property 4 (ONNX thread count binding): for any `cpu_cores` value in the range 1–256, when `ONNXEngine` loads a model, the ONNX Runtime session SHALL be configured with `intra_op_num_threads` equal to the passed `cpu_cores` value.
5. THE system SHALL implement Property 5 (orjson round-trip consistency): for any recommendation-shaped dict with string keys and int/float/str/None/list values, `_json_loads(_json_dumps(payload))` SHALL produce an object equal to the original payload.
6. WHEN any of Properties 1–5 fails for a generated input, THE test SHALL report the minimal failing example via the Hypothesis shrinking mechanism.
7. EACH property test SHALL be configured to run a minimum of 100 iterations via `@settings(max_examples=100)`.

### Requirement 5: Add Mutation Testing

**User Story:** As a platform engineer, I want mutation testing integrated into the CI pipeline so that the quality of the test suite is validated — not just its coverage percentage.

#### Acceptance Criteria

1. THE system SHALL integrate `mutmut` (or `cosmic-ray`) as a mutation testing tool targeting the `backend/serving_tier.py` and `backend/onnx_engine.py` modules.
2. WHEN mutation testing runs, THE Mutation_Testing tool SHALL report the mutation score (percentage of mutants killed by the test suite).
3. THE mutation testing step SHALL be runnable as a standalone CI job or script without requiring the full test suite to re-run.
4. THE `README.md` SHALL document how to run mutation testing locally.

#### Acceptance Criteria

### Requirement 8: Expand React SPA — Knowledge Graph Visualization Page

**User Story:** As a user, I want a Knowledge Graph page that visualizes the multi-hop graph paths using a force-directed graph, so that I can explore the semantic connections between movies.

#### Acceptance Criteria

1. WHEN a user navigates to the Knowledge Graph page and selects a seed movie, THE React_SPA SHALL fetch recommendations from `/v1/recommendations/knowledge-graph/{movie_id}` and render the results as a D3_Force_Graph.

### Requirement 13: Complete Adaptive-Serving-Tiers Spec — ONNX cpu_cores Wiring

**User Story:** As a platform engineer, I want the `ONNXEngine` to accept and apply the detected CPU core count so that ONNX Runtime uses all available cores for inference on Tier 2 deployments.

#### Acceptance Criteria

1. THE `ONNXEngine.__init__` SHALL accept a `cpu_cores: int = 0` parameter and store it as `self._cpu_cores`.
2. WHEN `ONNXEngine.load_model` creates an ONNX Runtime session, THE session SHALL be configured with `intra_op_num_threads` equal to `self._cpu_cores`; WHEN `self._cpu_cores` is 0, THE session SHALL use 0 to allow ONNX Runtime to auto-detect the optimal thread count.
3. THE `ONNXEngine` SHALL expose a `has_any_onnx_models(self) -> bool` method that returns `True` if and only if at least one ONNX session loaded successfully.
4. THE `get_onnx_engine(cpu_cores: int = 0)` singleton factory SHALL pass the `cpu_cores` argument to the `ONNXEngine` constructor.

### Requirement 14: Complete Adaptive-Serving-Tiers Spec — Ensemble Device Placement

**User Story:** As a platform engineer, I want the `ApexEnsembleEngine` to accept a device parameter and move all models to the specified device, so that Tier 1 deployments with a GPU use CUDA acceleration.

#### Acceptance Criteria

1. THE `ApexEnsembleEngine.__init__` SHALL accept a `device: str | None = None` parameter and store it as `self._device = device or "cpu"`.
2. WHEN `self._device != "cpu"`, THE `ApexEnsembleEngine.__init__` SHALL call `self._move_to_device()` after constructing all six sub-models.
3. WHEN `self._device == "cuda"`, THE `ApexEnsembleEngine.__init__` SHALL call `self._try_compile_all()` after moving models to the device.
4. THE `_move_to_device()` method SHALL call `.to(self._device)` on each of the six sub-models with a per-model try/except that logs a WARNING on failure without aborting.
5. THE `_try_compile(name)` method SHALL call `torch.compile` on the named sub-model, set `self._compiled[name] = True` on success, and log a WARNING and set `self._compiled[name] = False` on failure.
6. THE `_try_compile_all()` method SHALL call `_try_compile(name)` for each of the six sub-models not yet compiled.
7. THE `get_apex_engine(device: str | None = None)` singleton factory SHALL pass the `device` argument to the `ApexEnsembleEngine` constructor.

### Requirement 15: Complete Adaptive-Serving-Tiers Spec — Tier 3 Recommender Constraints

**User Story:** As a platform engineer, I want the `Recommender` to read the active serving tier at load time and apply Tier 3 constraints, so that low-memory deployments do not attempt to load neural models or build large indexes.

#### Acceptance Criteria

1. WHEN `Recommender.load()` is called, THE Recommender SHALL call `resolve_serving_tier()` from `backend.serving.serving_tier` to determine the active tier.
2. WHEN the active tier is `tier3`, THE Recommender SHALL set `self._low_memory = True` regardless of the `NOVA_LOW_MEMORY` environment variable; this override SHALL NOT be suppressible by any environment variable.
3. WHEN the active tier is `tier3`, THE Recommender SHALL cap the TF-IDF vocabulary at 12,000 features by setting `NOVA_TFIDF_MAX_FEATURES` to `"12000"` if the current value is higher.
4. WHEN the active tier is `tier3`, THE Recommender SHALL defer building the sparse retrieval index (not call `_build_sparse_retrieval_index()` at load time).
5. WHEN the active tier is `tier3`, THE Recommender SHALL skip loading the Diffusion model.

### Requirement 16: Complete Adaptive-Serving-Tiers Spec — Lifespan Tier Init and /health Extension

**User Story:** As a platform engineer, I want the FastAPI lifespan to initialize the TierDetector and branch engine startup by tier, and the `/health` endpoint to expose tier fields, so that the serving stack is fully tier-aware from startup.

#### Acceptance Criteria

1. WHEN the FastAPI application starts, THE lifespan function SHALL call `get_tier_detector().resolve()` to determine the active tier before any model loading.
2. WHEN the active tier is `tier1`, THE lifespan SHALL call `get_apex_engine(device="cuda" if gpu else "cpu")` and start the `OnlineLearner`.
3. WHEN the active tier is `tier2`, THE lifespan SHALL call `get_onnx_engine(cpu_cores=N)` where N is the detected CPU core count; IF `has_any_onnx_models()` returns False, THE lifespan SHALL override the tier to `tier3` and log a WARNING.
4. WHEN the active tier is `tier3`, THE lifespan SHALL not pre-load any engine; the recommender SHALL load lazily on the first request.
5. WHEN a GET request is made to `/health`, THE Health_Endpoint SHALL include `serving_tier`, `hardware_profile`, and `tier_selection_reason` fields populated from the `TierDetector` singleton.
6. IF the `TierDetector` has not yet completed detection at the time of a `/health` request, THEN THE Health_Endpoint SHALL return `"serving_tier": null` and `"tier_selection_reason": "detection_pending"` without blocking.
